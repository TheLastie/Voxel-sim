Продолжай разработку общего воксельного физического движка по `WORLD_PARADIGM.md` и инструкциям `AGENTS.md`. Это незавершённая долгосрочная цель: не объявляй парадигму реализованной, пока остаются отсутствующие крупные системы.

## Сначала проверь состояние проекта

1. Выполни `pwd`, `git status -sb`, `git log -5 --oneline` и проверь чтение нужных Markdown-файлов и возможность записи в рабочую папку. Не перезаписывай пользовательские изменения.
2. Прочитай `AGENTS.md`, `WORLD_PARADIGM.md` и `PROGRESS_2026-10-12.md` целиком или нужные разделы перед изменением поведения движка.
3. Проверь текущие `HEAD`, `origin/main`, доступность GitHub и состояние live viewer. Сведения ниже — снимок на 2026-10-13, их нужно перепроверить.

## Текущая подтверждённая база на 2026-10-13

- Ветка `main`, известный `HEAD` — `de8bbc0` (`Cache active PCG neighbor rows`), локально было 15 коммитов сверх `origin/main`, незакоммиченных изменений не было. Эти значения могли измениться.
- В движке есть общий API сцены и вокселей, кинематическая фиксация, удаление REV за мировыми границами с ledger для массы, импульса и энергии, энтальпийное состояние фаз и первая модель теплопроводности между связанными соседями.
- Сборка `cargo check --release --no-default-features --all-targets` проходила после последних описанных изменений. Тепловой поток и сохранение энергии ещё не проверялись физическим опытом.
- На Intel Core i5-14450HX сцена из 10 747 REV, шаг 1 мс и 4 подшага выполняла физический capture примерно за 40 секунд на 210 шагов (около 5,3 шага/с). Фиксация не дрейфовала; за этот короткий прогон связей не порвалось. Цель 30 FPS CPU не достигнута.
- Прямой CUDA probe и sparse matvec на GPU запускались, но это синтетические замеры. Полного GPU-физического решателя нет; цель 60 FPS GPU не измерена.
- Последний известный viewer работал на `http://127.0.0.1:8765` и показывал CSV/GIF/MP4. Перед новым физическим прогоном проверь, что он действительно отдаёт актуальную запись.
- Push не подтверждён: обычный Git push упирался в авторизацию, а запасной API-путь был отклонён автоматической проверкой. Не называй локальные коммиты опубликованными. Сначала проверь доступный авторизованный путь и фактическое изменение удалённой ссылки.

## Следующий конкретный шаг

Проверь теплопроводность как поведение движка, а не как отдельную физику эксперимента:

1. Изучи API и реализацию теплопереноса в `src/scene.rs`, solver и существующие probes/captures.
2. Подготовь воспроизводимую маленькую сцену с горячими и холодными соседними REV. Используй публичный API движка и зафиксируй материал, массу, геометрию, шаг времени и настройки решателя.
3. Проведи физический прогон, проверь направление потока, монотонное выравнивание температур и баланс полной внутренней энергии с учётом границ допуска метода. Если EOS или API мешают корректной проверке, исправь их на уровне движка.
4. Если для визуализации нужен новый формат, расширь viewer так, чтобы он показывал актуальный CSV/кадр и сохранял GIF. Не подменяй физические траектории синтетическими данными.
5. Запиши фактические настройки, численные результаты, сбои и ограничения в `PROGRESS_2026-10-12.md`. Если проверка не прошла, укажи конкретную причину и следующий диагностический шаг.

Затем продолжай незакрытые пункты `WORLD_PARADIGM.md`: термомеханическая связь, температурное изменение прочности, химия и реакции, слияние/сварка, жидкости, агрегация активной зоны, энергетический учёт и масштабируемость. Сначала добавляй общее поведение и удобный публичный API в движок (`src/`), затем показывай его в примерах.

## Правила выполнения

- Для каждого физического запуска сначала проверь чтение/запись и подними либо проверь live viewer на `http://127.0.0.1:8765`. Во время запуска публикуй CSV в viewer и сохраняй GIF, доступный на сайте. Проверяй, что страница отдаёт именно текущий прогон.
- Сохраняй реальные результаты симуляции. Рядом с визуализацией сообщай о разрушениях, дрейфе и других сбоях.
- Не простаивай, пока долгое выполнение занято в терминальной сессии: работай над независимой документацией или просмотром кода и периодически проверяй прогресс. Не запускай конкурирующие тяжёлые CPU-задачи во время замера производительности.
- Если есть срок, сверяй локальное время в `Asia/Yekaterinburg` и сначала обеспечь запускаемый, обозримый результат. Не заявляй целевой FPS без замера.
- Соблюдай парадигму: физические правила принадлежат движку, ограничения и масса — разные понятия, изменения топологии должны обслуживать все индексы и кэши, единицы SI указывай явно.
- До коммита просмотри `git diff` и `git status`; коммить связные завершённые этапы. Push выполняй только при наличии действующей авторизации и проверяй, что удалённая ссылка действительно сдвинулась.

Начни с проверок состояния и документов, затем выполни тепловую валидацию. В конце дай краткий отчёт: что изменено, чем проверено, точные измерения, ссылка на GIF/viewer, известные ограничения, commit и подтверждён ли push.
