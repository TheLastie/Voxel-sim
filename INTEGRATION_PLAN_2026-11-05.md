## 2. Интерфейс движка

Принципы: каждое действие в окне имеет проверенный путь в коде; MCP и окно вызывают один и
тот же API; элемент без работающего действия удаляется.

1. **Один путь для окна и MCP.** Сейчас Save/Load физического состояния, ручные связи и
   `MakeUnique` есть в документах и MCP, а в окне — только часть. Правило: новый API
   добавляется в `Scene`/`SceneDocument`, затем получает пункт меню и MCP-инструмент, оба
   с тестом.
2. **Панель запуска.** Состояние (Run / Pause / Failed), измеренная скорость мира,
   стоимость шага из полного worker, отставание, число активных REV и режим решателя
   (ячейки или трансляция). Это уже частично есть в метриках; нужна одна панель.
3. **Справка по клавишам (F1)** только из реально привязанных клавиш, с тестом, что каждая
   запись есть в обработчике.
4. **Инспектор состояния:** температура, энергия, повреждения, масса; для существа — запасы,
   сенсоры, активность сети. Данные берутся из `physics_metrics`, новых вычислений нет.
5. Проверка: тесты разметки `Ui` при 1920×1009 и 1280×720 (как существующие). Визуальная
   проверка окна остаётся ручной и должна быть отмечена в отчёте как невыполненная.

## 3. Существа: мозг, органы, обучение

Архитектура взята из `WORLD_PARADIGM.md` §2.4; порядок — как там: **ресурсы → сенсоры и
приводы → простой контроллер → LIF-сеть и обучение → перенос и повреждения**.

- **Данные.** `Genome` (строение, параметры органов, начальная раскладка сети, правила
  изменчивости) и `LearnedState` (веса и память жизни) — разные типы; наследуется только
  геном. Узлы мозга и органов имеют устойчивые идентификаторы и принадлежат существующим
  REV: масса и энергия считаются один раз.
- **Граница управления.** Контроллер (клип, написанный вручную, сеть) выдаёт коэффициент
  силы 0..1 каждому приводу. Привод создаёт силы через решатель; позы не записываются.
  Эта граница общая для редактора и мира.
- **Энергия.** Работа мышцы списывается из запаса, потери уходят в тепло REV мышцы;
  контроллер не может обойти запас. Голод и сытость выводятся из запасов и пищеварения,
  флагов нет.
- **Бюджет.** Сеть до 256 нейронов; расчёт идёт с шагом 1–2 мс внутри 10 мс физики.
  Ориентир: не больше 0,1 мс на существо и 5% от бюджета 5 мс при 20 существах в прогрузке.
  Стоимость сети, органов и приводов видна отдельно (счётчики спайков и операций).
- **Вне прогрузки.** Существо без детальной механики сохраняет запасы, возраст и цель
  и переходит на редкие шаги по событиям; при уточнении состояние восстанавливается.
- **Обучение.** Начинается с ограниченного вознаграждаемого обновления весов на простой
  задаче; обучение ходьбе — отдельный этап после проверки движения паука с контактами.
  Заранее записанный клип сам не считается ни сетью, ни обучением.

## 4. Растения: ресурсы и процедурный рост

Текущий рост — приближение. Цель — модель из `TREE_GROWTH_MODEL.md` с проверяемыми законами.

1. **Ресурсный учёт растения:** углерод/энергия, вода, минералы; биомасса берётся из почвы и
   воздуха (масса сохраняется), потребители (корни, ствол, ветви, листья, плоды)
   конкурируют по правилам распределения; кольца роста и жёсткость дерева выводятся из
   этих запасов, а не из таблицы.
2. **События вместо покадрового пересчёта.** Растение хранит геном, возраст, запасы,
   повреждения и время следующего события (смена сезона, ветвление, созревание, гибель).
   Участок с постоянными условиями интегрируется аналитически; пропуск считается
   интегрированием, не остановкой жизни.
3. **Свет и конкуренция** — на грубой сетке тени, обновляемой редко; соседи влияют
   по физическому времени.
4. **Срубание.** Разрез меняет связи сразу; неповреждённые части движутся как
   укрупнённые тела; отрубленная часть перестаёт получать воду и свет, но сохраняет массу
   и состояние. Обязательные проверки: нет зависания кадра, масса и энергия сохраняются.
5. **Наследование.** Мутация и размножение — через явные правила генома; распределения
   признаков имеют обычные значения и редкие крайние, границы заданы явно.
6. **Геометрия** строится фоновыми задачами по порциям; физические REV вблизи камеры — 1 см.

## 5. Путь оптимизации к 5 мс на 10 мс

Факты (`VALIDATION_2026-11-05.md`): блок железа 16 000 ячеек на 16 потоках CPU — около 3 с на
шаг (сборка блоков 0,6 с, построение иерархии 0,3 с, CG 1,9 с при ~17 решениях и 27 итерациях).
До бюджета — около 600×. Одним улучшением такой разрыв не закрыть; нужна цепочка:

| Шаг | Идея | Оценка выигрыша | Проверка |
| --- | --- | --- | --- |
| A | Убрать лишние решения на подшаг: единая проекционная задача для контакта и трения вместо активных наборов по очереди | 2–4× | число решений на шаг, эталоны |
| B | Переиспользовать иерархию и блоки между подшагами при неизменных масках; пересобирать только при изменении | 1,5–2× | итерации, эталоны |
| C | Резидентный GPU-путь на `wgpu` для ячеек: SpMV, Якоби, ограничение/продолжение, V-цикл без возврата векторов на CPU; крупный уровень — плотная факторизация | 20–50× по пропускной способности памяти | паритет с CPU по невязке, счётчики байт |
| D | Адаптивные области: покоящееся равновесие спит, детальные ячейки только у событий | зависит от сцены | сохранение энергии и импульса при пробуждении |
| E | Укрупнение отдалённых тел (агрегаты) с точным раскрытием | зависит от сцены | эталоны с раскрытием |

Оценка идёт по измеренному трафику: `время ≥ байты / полоса + запуски + зависимости`.
Пример на 50k ячеек: матрица блоков 6×6 FP64 порядка 150 МБ на умножение; 30 итераций ×
3 умножения ≈ 13 ГБ на решение, при 400 ГБ/с — 30 мс. Это уже выше бюджета только на
одно решение: нужны FP32 для векторов и блоков, меньше итераций и меньше решений, и
**достижимость 5 мс на 50k активных тонких REV пока не доказана**. Если нижний предел
окажется выше бюджета, в отчёте остаётся ограничение, а не скрытый расход.

Правила: CUDA — только дополнительный путь NVIDIA; портируемый путь `wgpu` обязателен
(Windows: NVIDIA, AMD, Intel); для AMD и Intel заявлять поддержку только после реального
запуска; CPU-путь остаётся проверяемой базой.

## 6. Порядок работ

1. Закоммитить многоуровневый решатель ячеек (сделано, см. журнал).
2. Слить ветки субагентов после проверки: `feature/editor-usability`, `feature/creature-brain`.
3. Шаги A и B из §5 (CPU, измеримо на паука и блоке); затем C — GPU-прототип одного V-цикла
   на малых системах с паритетом.
4. Существа: сенсоры из реального состояния сцены → контроллер → сеть → обучение простой
   задаче → проверка паука с контактами.
5. Растения: ресурсный учёт с сохранением массы → события вместо кварталов → срубание.
6. Ступени 1k → 16k → 50k: полный worker, p50/p95/max, фиксированная сцена с контактами,
   деформацией и разрушением.

Для каждого шага: изменённые файлы, точные команды, замер до и после, энергетический баланс,
известные ограничения. Цели 50k и 5 мс остаются открытыми до воспроизводимого замера.
