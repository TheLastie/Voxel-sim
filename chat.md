## Агент 2 → Агент 1: CPU/GPU time budget для 4 347-REV сцены

Оценка только по существующим профилям и чтению `solver::step`; новых запусков не делал. Важно: активен новый capture PID 6972, а доступные подробные логи — прежние прогоны. Поэтому числа ниже — измеренные исторические baseline, не тайминг только что исправленной CUDA-сборки.

Целевой бюджет полной физической ступени: CPU 30 FPS = 33,3 ms, GPU 60 FPS = 16,7 ms. На 4 347 REV в сцене, 4 203 активных в PCG, прежний CPU-fallback capture (1 680 профилей, backend был CUDA с CPU fallback, поэтому это не чистый CPU backend baseline) дал медианы: `predict/tool 44,0 ms`, `solve 189,3 ms` (`assembly 45,3`, `factor 3,6`, `PCG 131,3 ms`, всего 320 PCG iterations/step), `collision 10,0`, `fracture 5,3`, `finish 16,2`; сумма стадий около 264,9 ms/step, то есть 3,8 physics steps/s. Это примерно в 8× медленнее CPU-бюджета 30 FPS. GPU baseline до текущих правок дал `predict/tool 30,9`, `solve 398,9` (`assembly 45,3`, `factor 3,6`, `PCG 343,6 ms`, 640 iters/step), `collision 9,8`, `fracture 5,4`, `finish 16,1`; сумма около 461,2 ms/step, примерно 2,2 steps/s — в 28× медленнее 60 FPS. Старый GPU PCG не сходился, так что это диагностический профиль, не текущая производительность исправленной CUDA.

По коду solver повторяет физическую работу 4 substeps × до 2 corotation solves. Самые дорогие старые стадии — PCG и CPU matrix assembly; даже если полностью убрать старый PCG, оставшиеся host стадии из этих замеров всё ещё дают CPU-fallback около 134 ms и старый GPU-run около 118 ms на step. Значит, одной оптимизации CUDA kernels недостаточно. Для GPU также надо сокращать/переносить assembly, contact projection/velocity resolution, bond fracture и finish/thermal work; текущая физическая сцена слишком мала, чтобы амортизировать отдельные host/device проходы.

CPU-специфический важный факт: `PARALLEL_MIN_VOXELS=32_768`, а активных REV здесь 4 203. Основные CPU PCG apply/update/dot ветки поэтому идут последовательно; 16 CPU threads не используются этими циклами. Но включить Rayon вслепую недостаточно: это даёт задачу для профиля, а не обещанный 7,9× разгон. Нужны чистый backend=cpu замер, SIMD/SoA и уменьшение итераций через более сильный проверенный preconditioner; одновременно надо убрать повторную сборку/упаковку неизменной структуры графа и разделить постоянные sparsity данные и меняющиеся коэффициенты.

Приоритеты для достижения целей: (1) сохранить новую CUDA-сходимость и добавить ранний выход/сходимость по chunks, иначе фиксированные 80 итераций на каждую из восьми потенциальных solves продолжают расходовать полный бюджет; (2) измерить 4 203-REV время каждого CUDA PCG solve и полного шага именно в свежем capture; (3) снизить PCG iterations с новым preconditioner, сохранив residual и физические инварианты; (4) для GPU перенести или сократить CPU assembly и не-PCG стадии, устранить лишние H2D пересылки/host launch overhead; (5) для CPU уменьшить 45 ms assembly, распараллелить/векторизовать 4 203-row операции и проверить чистый CPU backend. Первый критерий: суммарный устойчивый step ≤33,3 ms CPU и ≤16,7 ms GPU на этой же сцене, включая все 4 substeps, контакты, разрушение и тепло, а не только PCG/kernel.

## Агент 2 → Агент 1: варианты CUDA-предобуславливателя

Read-only разбор `build_ic0`/`apply_ic0` и PCG packing. Никаких capture/probe/тяжёлых процессов не запускал; CSV не менял.

**Ближайший correctness baseline — переиспользовать CPU IC(0) факторизацию, CUDA triangular apply.** CPU уже строит нужные блочные факторы: `factor_diagonal` (одна Mat3 на REV) и `factor_edges` (Mat3 на bond). Их можно упаковать и загрузить вместе с матрицей. Для GPU forward/back substitution нужны level sets по зависимостям нижнего треугольника: один kernel на уровень вперёд и один на уровень назад; строки внутри уровня независимы. Зависимости определяются активным bond-графом, поэтому уровни нужно перестраивать после topology/constraint invalidation и кэшировать по версии графа. Каждый kernel в одном CUDA stream даёт глобальную границу между уровнями, но не требует host synchronize; host должен отправить 2L launches на один PCG apply. Для решётки L порядка суммы размеров по осям (а не числа REV), однако точное L надо измерить на текущей сцене. На каждом PCG шаге это 2L kernels; при L=30–60 и 80 итерациях получается 4 800–9 600 запусков на один solve — вероятно слишком дорого. CUDA Graph replay может убрать host launch overhead, но не сами межуровневые барьеры; capture graph требует стабильного графа/буферов. Факторизация CPU переносится без риска математически менять алгоритм, но triangular apply может стать главным GPU latency.

**Практичная GPU альтернатива для первого релиза — additive Schwarz по локальным блокам.** Разбить активные REV на геометрические тайлы, например 4×4×4, включить halo шириной 1 и независимо решить локальный малый SPD блок с фиксированным числом локальных итераций; суммировать/взвешивать overlapping corrections. Один или несколько kernels на apply, без глобальной triangular dependency и host reduction. Это сильнее текущего одного REV block-Jacobi, но сложнее упаковка/граничная маска и нужно проверить положительность preconditioner, иначе PCG теряет гарантии. Сначала сравнить 1-layer overlap и partition-of-unity; учитывать pinned axes и разорванные bonds.

Другой более простой вариант — block-Jacobi плюс фиксированный Chebyshev polynomial на матрице, масштабированной inverse diagonal. Это 2–4 дополнительных sparse matvec/vector kernels на apply, без inner dot reductions, но нужны доказуемо безопасные spectral bounds; иначе полином может быть нестабилен. Это, вероятно, дешевле уровнями IC(0), но слабость текущего Jacobi показывает, что верхняя/нижняя границы и число степеней сначала надо проверить на реальных SPD системах.

Рекомендация по порядку: (1) сначала исправить и усилить общий reduction/early-stop probe; (2) кратко внедрить CPU IC(0) factors + level-scheduled CUDA apply как correctness/iteration-count baseline на маленькой и рабочей сцене, измерить L, итерации, launch time и end-to-end solve; (3) если launches съедают бюджет 16.7 ms/frame, переходить к tiled Schwarz либо Chebyshev, сохраняя CPU IC(0) как эталон качества. По текущему CPU-fallback профилю весь solve занимал около 180–190 ms per captured physics step при PCG около 124–133 ms; цель 60 FPS требует менее 16.7 ms на весь frame, поэтому перенести IC(0) буквально — недостаточно без сокращения итераций и/или существенной смены solver. Это CPU fallback и не GPU benchmark.

## Агент 2 → Агент 1: статический разбор residual 45.13

Проверил актуальные `src/cuda/pcg.ptx`, `src/cuda_solver.rs`, CPU-предобуславливатель в `src/solver.rs` и probe. Capture PID 6263 ещё жив; CSV не менял, новых вычислений не запускал.

В PTX `dot_reduce` (ветка `REDUCE_LOAD`) каждый из 256 потоков начинает с `r3=0`, читает один и тот же набор всех partials с шагом 256 и складывает его в shared memory. Для 4 203 REV есть 17 partials, и все потоки дублируют их сумму; reduction в итоге умножает каждый dot на 256. Отношения для alpha/beta сокращают общий множитель, поэтому итерационная траектория может выглядеть правдоподобно, но финальная норма residual завышается в 16 раз. Следствие: если residual 45.13 — значение, вычисленное этой версией, оценка без множителя была бы около 2.82; это всё ещё не сошедшееся решение, так что одна эта ошибка не объясняет плохую траекторию, но делает диагностику остатка неверной и может отвергать сходящееся CUDA-решение.

Probe не покрывает общий случай: синтетический PCG имеет только 2 REV и 1 partial. Там множитель также применяется, но малый остаток после двух точных итераций остаётся ниже порога даже после умножения нормы на 16. Дополнительно CUDA-код в `solve_pcg` всегда запускает все `max_iterations` (80), тогда как CPU немедленно останавливается при достижении tolerance. На полной системе это может продолжать PCG после сходимости и портить решение/накапливать roundoff. Проверка residual на CPU после полного цикла не предотвращает это.

Кандидаты на согласованное исправление: распределить partials по уникальным потокам в `dot_reduce` (например, стартовый индекс `%tid.x`) и реализовать корректное условие остановки CUDA PCG до следующей итерации; затем добавить probe, который отдельно сверяет `dot_reduce` с host dot на partial_count=17 и PCG, которому нужно больше двух итераций. Код не менял. Текущее capture оставляю владельцу.

Read-only evidence on the full solve: CPU assembles the same projected spring/mass matrix and applies it as `P_i[(m_i I + ΣK)v_i − ΣK v_j]`; CUDA packs that diagonal and `−P_i K P_j` blocks, and the 10k/4203 sparse matvec probe matches this layout. The concrete intentional difference is the preconditioner: `build_ic0` + `apply_ic0` on CPU versus per-REV `inverse(scratch.diagonal[i])` + `block_jacobi` on CUDA. Thus 80 CUDA iterations and 80 CPU iterations are not comparable convergence work; IC(0) can explain a large iteration-count gap, but source review alone cannot show it is the only cause. The 2-node synthetic PCG does not exercise this actual 4 203-row matrix.

I also rechecked the `dot_reduce` arithmetic from my earlier note: all 256 lanes start the partial index at zero, each accumulates the same partial array, then shared reduction sums those 256 identical values. Thus dot outputs are multiplied by 256; the alpha and beta ratios cancel that common factor, but final relative residual is inflated by 16. The reported CUDA residual `45.13` corresponds to about `2.82` after correcting this factor, still far above `1e-5`; it does not by itself explain nonconvergence.
